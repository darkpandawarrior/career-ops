# conformance/

A language-neutral corpus of `(input -> expected output)` cases for functions
that **both** hiresignal-js (this repo) and the Kotlin Multiplatform rework
(`~/Repos/Android/HireSignal`) must agree on byte-for-byte, because they
independently write or read the same files on disk: `data/applications.md`,
`data/pipeline.md`, `data/scan-history.tsv`.

## Why this exists

`core/engine/engine-port-manifest.tsv` + `EnginePortDriftTest` on the Kotlin
side already catch the JS **original moving** — a hash tripwire on the vendored
`external/career-ops` submodule. That tells a maintainer "go look, something on
the JS side changed." It cannot tell them the two implementations still
**agree** — it has no idea what "agree" even means for a given function. This
kit is what "agree" means, made runnable: a fixed corpus of inputs and their
correct outputs that any implementation, in any language, can replay.

The specific risk closed here: `sanitizeTsvField` / `sanitizeMarkdownField` /
`sanitizePipelineUrl` decide the literal bytes written into the user's real
tracker and pipeline files. They are kept identical between the two repos by
code comments alone today. `scan.mjs` escapes `\ [ ]` in **one** regex pass —
each match is resolved against the original string, so there is no
order-dependence in the JS. A hand-ported Kotlin implementation doing three
sequential `.replace()` calls *is* order-dependent: get the order wrong and a
value containing both a backslash and a bracket comes out different, while
every value containing only one or the other still matches by coincidence. See
`fixtures/sanitizers.json`'s `*_then_*` / `backslash_bracket_combo_realistic`
cases — those are the ones designed to catch exactly that reordering.

## How a second implementation consumes this

Each file under `fixtures/` is plain JSON: read it with whatever your
language's standard JSON parser is, iterate the cases, call your own
implementation of the same function, and assert equality (or the file's
`matchRule`, if it states one — `status-aliases.json` does, because its
oracle function returns a token, not the canonical label verbatim). No JSON
schema, no code generation, no shared tooling required — that is deliberate,
so a Kotlin (or any other) test suite can consume this with nothing more than
`kotlinx.serialization` or even hand-rolled parsing over a small file.

Every fixture file carries:

```jsonc
{
  "schemaVersion": 1,       // bump only on a breaking shape change
  "provenance": "extracted" | "authored",   // see below — READ THIS FIRST
  "provenanceNote": "...",  // what backs this file's claim to correctness
  // ... function-specific case list ...
}
```

`sanitizers.json` groups cases under `functions.<fnName>`, one array per
sanitizer. `status-aliases.json` is single-function and carries `cases`
directly, plus a `matchRule` describing exactly how to compare
`canonStatus`'s return value against a case's `expectedLabel`.

Every case is `{ id, input, expected(...), note? }`. `id` is stable and
descriptive — use it in a failure message so a human can find the case by
name, not by array index. `note` is optional but present on nearly every case
here; read it before assuming a value is a typo — several encode a genuinely
surprising, deliberate behaviour (see below).

## `verify-js.mjs` — proves the extraction is faithful, not just present

Run:

```bash
node conformance/verify-js.mjs
```

It loads every file in `fixtures/`, calls the **live** JS function for every
case, and fails loudly (non-zero exit, one block per mismatch showing
input/expected/actual) on any disagreement. This is also wired into the
engine's own discovered suite as `tests/conformance.test.mjs` (run via `node
test-all.mjs`, or narrow to just this file with `node test-all.mjs --only
conformance`), so a fixture drifting from the JS it describes fails CI the
same way any other regression does — it does not require a human, or the
Kotlin side, to notice first.

**What this does and does not prove.** For a fixture whose `provenance` is
`authored`, running clean here only proves internal consistency: the fixture
and the JS agree *because the fixture's expected values were generated by
running that same JS*. It is not independent evidence of correctness. For
`extracted` fixtures it's stronger, because the case was pulled from an
assertion an existing, independently-written test already makes — see below.

## `extracted` vs `authored` — the rule that matters most

Every fixture file, and ideally every case, is one of exactly two things:

- **`extracted`** — pulled from an implementation's *existing* tests, so it
  encodes behaviour someone already wrote a test to verify, independently of
  this kit. `status-aliases.json` is this: the alias/label enumeration comes
  from `templates/states.yml` (the file both systems already contract to as
  their source of truth — see its own header comment), and the trickiest
  cases — the capitalised Turkish dotted-İ fold, a markdown-bolded status, the
  empty/dash → Discarded fallback — are copied verbatim from the assertions in
  `web/src/lib/status-alias.test.mjs`, which already runs in CI and already
  encodes *why* each of those is correct (see that file's own comments).

- **`authored`** — hand-written by looking at the implementation and deciding
  what it should do, with `expected` filled in by running the live function
  once. This freezes *current* behaviour. It does **not** prove that behaviour
  is *correct* behaviour — an authored fixture for a function with no
  pre-existing test can just as easily encode a latent bug as a real
  guarantee, and nothing about a clean `verify-js.mjs` run distinguishes the
  two. `sanitizers.json` is entirely `authored`: before this kit existed, no
  test in `tests/` or `web/` called `sanitizeTsvField`, `sanitizeMarkdownField`,
  or `sanitizePipelineUrl` directly (confirmed by grep) — `tests/conformance.test.mjs`
  calling them now is this kit's own coverage, not pre-existing, independent
  proof. Treat every case in that file as "this is what it does today," not
  "this is provably what it should do."

If you add a fixture, decide which bucket it belongs in **before** writing
`expected`, and say so in the file's `provenance` / `provenanceNote` (or per
case, if a file ever mixes both). Don't let an authored fixture drift into
being treated as a spec.

## Findings surfaced while authoring `sanitizers.json`

Nothing here is a bug — each is a deliberate-looking asymmetry between the
three sanitizers that is easy to port wrong precisely because it looks like it
should be symmetric. Flagged rather than silently encoded:

1. **`sanitizePipelineUrl` truncates at the first whitespace; the other two
   collapse whitespace runs to a single space.** `normalizeScanUrl` does
   `.trim().split(/\s+/)[0]`, so `"https://x.com/a b"` becomes
   `"https://x.com/a"` — everything from the first internal space onward is
   silently **dropped**, not just squeezed. The other two sanitizers
   (`normalizeScanScalar`) never drop content, only whitespace runs. A port
   that reuses one "normalize" helper for all three fields will get this one
   wrong in a way nothing but a real space-containing URL will surface. See
   `internal_space_truncates` / `internal_newline_truncates` /
   `internal_tab_truncates`.

2. **Pipe is escaped to a different literal per function, not a shared
   constant.** `sanitizeMarkdownField` turns `|` into `/`; `sanitizePipelineUrl`
   turns it into `%7C` (URL-percent-encoding), because that value is a literal
   URL riding inside the same markdown table cell — encoding it as `/` would
   silently corrupt the URL. `sanitizeTsvField` doesn't touch `|` at all
   (correctly: it's tab-delimited, a pipe is just data). See `pipe_single` /
   `pipe_multiple` in `sanitizeMarkdownField`, `pipe_url_encoded` in
   `sanitizePipelineUrl`, and `pipe_untouched` in `sanitizeTsvField`.

3. **Only `sanitizeTsvField` guards against CSV-injection leading characters**
   (`= + - @`). `sanitizeMarkdownField` and `sanitizePipelineUrl` do not —
   `csv_injection_char_not_escaped` cases in both files pin that a leading `=`
   is left alone there. This is presumably fine (Markdown table cells and URL
   columns aren't opened in a spreadsheet the way a `.tsv` is), but it is an
   asymmetry, not an oversight to "fix" by making all three consistent without
   checking why the TSV guard exists in the first place.

None of these look wrong given what each function is *for* — but all three
are exactly the kind of "looks equivalent, isn't" detail an audit finds months
late, which is the whole reason this kit exists.

## Scope (v1)

Covered:

- `sanitizeTsvField`, `sanitizeMarkdownField`, `sanitizePipelineUrl`
  (`scan.mjs`, all `export`ed — `sanitizePipelineUrl` was internal until this
  kit needed to call it directly; the sanitizing logic itself is unchanged).
- `canonStatus` / the `templates/states.yml` alias table, exercised through
  `web/src/lib/status-alias.mjs`'s `canonStatus`, the only implementation of
  the fold+lookup that already had a states.yml-drift test guarding it.

Deliberately **not** covered in v1 (scope it up when a second divergence in
one of these turns up — don't pre-build against a hypothetical):

- `formatPipelineOffer` / `formatScanHistoryRow` (compose the sanitizers above
  plus positional-column logic; a fixture here would mostly be re-testing
  column layout, which the manifest/drift-test approach already watches via
  hashing the source).
- The tracker lock protocol (`pipeline-lock.mjs` / `tracker-lock.mjs` /
  `portal-health-lock.mjs`) mentioned in this work's background — genuinely
  higher-value than what's here, but its behaviour is concurrency/IO-shaped
  (advisory locks, retry/backoff, stale-lock detection) rather than pure
  input→output, so it needs a different fixture shape (a sequenced scenario,
  not a table of cases) and was out of scope for this pass.
